# Отказ обновления 0.7.5 и исправление 0.7.6

## Подтверждённые факты

На рабочем ПК после попытки обновления работала целая 0.7.4 с флагами `--update-failed --skip-update=0.7.5`. SHA-256 загруженного Win11-пакета 0.7.5 совпал с официальным выпуском. Все 525 файлов восстановленной установки совпали с её манифестом. Повреждения скачанного файла и смешанной установки не обнаружено.

Старый обновлятор наследовал текущий каталог приложения. NSIS для безопасной транзакции переименовывает весь этот каталог в резервную копию; живой процесс, удерживающий его как CWD, мешает переименованию. Дефект воспроизведён настоящими выпущенными двоичными файлами на синтетических данных:

| Обновлятор и пакет | Рабочая папка обновлятора | Результат |
|---|---|---|
| Официальный updater 0.7.4 и Win11-пакет 0.7.5 | Папка тестового App | updater exit1, осталась 0.7.4 |
| Те же двоичные файлы | Тестовая Updates вне App | updater exit0, установилась 0.7.5 |

Отдельно запись `InstallDir` в реестре на ПК указывала старую папку `ClipNest`, а фактический процесс находился в `ClipShot`. Автообновление не должно выбирать назначение по этой устаревшей записи. Поведение стандартного `InstallDirRegKey` описано в [справочнике NSIS](https://nsis.sourceforge.io/Docs/Chapter4.html#installdirregkey).

Старый updater не сохранял этапы отказа. Поэтому точную историческую строку исключения и вклад каждой проблемы в прошлую попытку восстановить нельзя. Это не меняет результата воспроизводимого опыта с CWD и фактического несовпадения каталогов.

## Исправление

1. Новое приложение и updater задают нейтральный CWD вне папки установки. То же правило действует при перезапуске приложения.
2. Поскольку обновление запускает **старый** updater, установщик 0.7.6 включает совместимый helper. После проверки одноразового handoff установщик запускает helper вне App и ждёт подтверждения приёма.
3. Helper до подтверждения удерживает проверенный EXE от изменения и сохраняет объект блокировки установки. Первый установщик завершается кодом4, старый updater штатно перезапускает приложение и выходит. Helper ждёт завершения обоих родителей и освобождения lease, затем выполняет обычную транзакцию установки.
4. Фактическая папка приложения берётся из проверенной команды непосредственного старого родителя. Проверяются цепочка процессов, имя updater, путь установщика, SHA, режим и тестовый корень. Подсказка NSIS из реестра не является источником истины.
5. Новый updater передаёт `/APPDIR` с фактической папкой. NSIS принимает его только при подтверждённом одноразовом handoff; тестовый маршрут ограничен своей веткой `TEMP/ClipShot.Tests/.../App`.
6. После установки проверяются ожидаемая версия EXE и целостность всех файлов, затем подтверждение запуска. Старая версия не может выдать себя за успешно обновлённую лишь записью health-маркера.

Атомарное переименование каталога, снимок поставляемых файлов, SHA и откат не заменены небезопасной перезаписью отдельных файлов поверх работающей установки. Журнал `Updates/updater-log.jsonl` содержит время, этап, режим, версии и технические коды ошибок; сообщения исключений, командные строки, личные пути и данные буфера туда не записываются.

## Проверки и ограничения

`scripts/Test-LegacyUpdaterBridge.ps1` использует закреплённый SHA официального установщика 0.7.4. Он запускает настоящий старый updater с CWD внутри App. Режим `-NestedActualApp` намеренно разводит фактическую папку процесса и начальный INSTDIR, не меняя настоящий реестр. Проверяются передача работы, новый payload целиком, сохранность синтетической истории/шаблонов/настроек и настоящий health-handshake. Этот сценарий включён в обязательный выпускной gate и проверку release evidence.

Тестовая health-ветка запускается только вместе с изолированным режимом и явным проверенным тестовым корнем; она никогда не открывает личную базу. Это устраняет прежний пробел, когда тест updater проверял лишь выход `--upgrade-self-test`, обходя production health.

Однократный переход со старого updater использует `NtQueryInformationProcess(ProcessCommandLineInformation)` для чтения **только уже подтверждённого родителя**. Это внутренний интерфейс Windows; [Microsoft предупреждает о возможных изменениях](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntqueryinformationprocess). При недоступности API или отказе проверки helper прекращает переход до подтверждения, не используя старый реестр как небезопасную подмену. Новые обычные обновления не нуждаются в этом переходном чтении команды.

Фактические результаты предварительного и окончательного прогонов записываются в `docs/STATUS.md`. Проверки на Windows 11 не объявляются реальным испытанием Windows 10/LTSC2019.
